# 零预算持续生产方法

## 1. 定位

本项目是 AI 辅助的个人清史研究库，不是专家审定的官方数据库。目标不是用长文章制造“很全”的观感，而是持续增加可回查、可修正的知识单元。

页面定位（不再挂固定横幅）：本站是 AI 辅助整理的个人研究稿，提供来源回查，但未经专业清史学者全面审校。0.6.0 起已撤除全库声明横幅与章节级研究草稿横幅（见 CHANGELOG）；「研究稿」定位靠状态徽标与说明文字表达，不靠页顶常驻条。

## 2. 零成本技术栈

- Markdown：人物卷、事件页、专题和争议卡；
- CSV/JSONL：人物、主张、关系、来源、图像和任务队列；
- 站点阅读层只消费构建出的 JSON；源真相仍是 CSV，不再派生 SQLite 或整表镜像；
- Git：版本、撤回和差异；
- 静态站点：本地浏览构建后的 `site/`；
- Mermaid：局部关系图和时间线。

现阶段不上付费数据库、云向量库、商业 OCR 或图数据库。数据规模没有大到需要这些东西，提前引入只会增加维护负担。

## 3. 数据生产链

```text
公开来源／馆藏目录
  ↓ 登记访问与权利
AI 提取候选（状态从「审核中」起步）
  ↓ 打开来源逐条回查，补逐字引文与卷页定位
AI 自审（npm run self-review：引文＋定位＋无冲突组 → 已采纳）
  ↓
用户顺手抽查（STATUS.md「建议顺手抽查」清单，不卡发布）
  ↓
叙事、关系图、时间线和本地页面
```

本项目无专家参与，页面与文档不得出现「专家审核／权威认证」字样；两个 Agent 相互检查也只算 AI 自审。

## 4. 状态轴

人物 ID 只有一个体系：`QH-P-*`。现有 `QH-E-*` 仅是第一批十二帝展示表的兼容 ID，迁移对照见 `data/entity-id-crosswalk.csv`。皇帝不是与“人物”并列的实体类型，而是人物在特定时间获得的称号；玄烨、胤禛、弘历不得因为同时出现在十二帝表和康雍样本表而生成两个人物实体。

### 证据状态（用于来源索引、统治年表等回查类表）

- `E2 多源回查`：至少两个真正独立的来源系统支持；
- `E1 单源回查`：已打开一个直接或权威来源；
- `S 二手转述`：当前只有现代或后出材料；
- `C 来源冲突`：可靠来源相互不一致；
- `U 待核`：尚未打开所称依据；
- `X 目前不可证`：已检索但公开材料不足。

主张的工作状态（审核中／已采纳）见 `docs/04-editorial-and-review-manual.md` §2，由 `npm run self-review` 维护。证据状态不得折算成一个假装精确的分数。

## 5. 一帝一卷、八个数据包

1. `P0 来源包`：资料目录、访问状态和许可；
2. `P1 身份包`：姓名、称号、生卒、即位、死亡和陵寝；
3. `P2 家庭包`：父母、后妃、皇子女、收养和礼法关系；
4. `P3 年表包`：事件、时间、地点和参与者；
5. `P4 统治专题包`：政治、军事、财政、边疆、社会和文化；
6. `P5 文献图像包`：《清史稿》《清实录》、玉牒线索、画像和文物；
7. `P6 争议审计包`：异说、冲突、流行传闻和待核项；
8. `P7 发布包`：叙事、局部关系图、时间线和质量报告。

生产顺序：康熙、雍正、乾隆、顺治、嘉庆、道光、咸丰、同治、光绪、宣统、皇太极、努尔哈赤。展示顺序仍按年代。开国两卷最后深挖，因为称号、政权定义、满文材料和前三朝实录版本问题最复杂。

## 6. 来源边界

- 明确公版、CC0、CC BY、CC BY-SA 的单项资源可以按许可保存与展示；
- 免费检索不等于可以镜像，一史馆和故宫等资源默认保存自建元数据、精确定位、必要短引文和原站链接；
- **「须到馆」「须机构账号」不构成停止理由**：先走公开可及路径——已刊档案汇编（《康熙朝汉文朱批奏折汇编》《雍正朝汉文朱批奏折汇编》等公开出版物）、机构公开在线检索目录、公共图书馆藏本、公共领域影印本、开放数据集；只有在这些路径全部走完后仍无入口，才登记缺口，并写明已尝试路径；
- Wikimedia Commons 必须逐文件打开说明页核许可，不能按分类页一键认定；
- 玉牒原件未见时统一写“玉牒待核”，不得把二手亲属表伪装成玉牒原文；但“待核”不等于停在此处——应继续找公开可及的玉牒路径（已刊／影印本、爱新觉罗宗谱一类公开出版物、机构公开检索目录），并在缺口记录中写明已尝试路径；
- 百度百科、自媒体、论坛、影视剧和 AI 记忆只能发现关键词，不得作为重要结论的唯一证据；
- 盗版扫描、绕过登录或访问控制的材料不使用。

## 7. 每轮工作大小

每轮只处理以下之一：

- 一个来源单元；
- 20—30 条原子主张；
- 一个关系子图；
- 一个专题小节；
- 5—10 件图像的逐件核权。

每轮必须更新 `data/task-queue.csv` 的完成位置、未决问题和下一步动作。上下文记忆不是项目管理系统，磁盘上的队列才是。

## 8. 写作建议（不设门槛）

下面是写作时的默认做法，**不是发布前置条件**——构建不会再因内容问题失败：

- 事实句尽量绑定主张或来源；
- 直接引文尽量能回到可见原文；
- 关系边标出证据状态；
- 本地嵌入图像有逐文件许可；
- 未采纳内容进入叙事时带状态徽标，不作定论句；
- 争议不压成唯一答案；
- 玉牒原件未见时标"待核"；
- 没有专家参与时，不写"权威""专家认证"字样。

严重错误包括认错人、错误亲属关系、日期年号错配、来源不支持结论、传闻写成同时代记录、推测写成事实和未经许可展示图片。发现后直接修掉即可，不再触发"整批重新开放检查"。

## 9. 冷酷的边界

“能有多详细就多详细”没有天然终点。若没有任务分片、证据状态和版本控制，这句话只会制造一堆无法复核的文字。零预算不是问题；真正的问题是想同时要全量、权威、速度和零人工检查。四者不可兼得。本项目选择零现金成本、持续扩充、可纠错，并明确放弃“已经完成全部清史”的虚假承诺。
