# 25 · 勘误流程

状态：已接通（2026-09-11）
前提：本站是**历史爱好者的资料网站，不是研究课题**。不做具书核录，错误留到阅读时发现再改。

---

## 一、为什么是这样一套流程

本站的准确性策略不是「先把所有材料核一遍再发布」，而是：

```text
先用可及的公开材料把内容做出来 → 读者（= 你）读的时候发现不对 → 记一行 → 改掉 → 留档
```

这个策略成立的前提只有一个：**出处必须是真的**。所以有一条不让步的红线——

> **不编造来源；引文与「卷页/档号/图像定位」必须对得上。**

理由与学术无关，与流程本身有关：你读到某处觉得不对时，我判断的依据就是那个出处。出处一旦不可信，勘误就退化成猜，「读到再问」这件事本身就不成立了。这条成本最低（引文本来就在库里），收益最直接。

---

## 二、怎么提一条勘误

### 推荐：一条命令

```bash
npm run errata -- --loc <位置ID> --text "<发现的问题>" \
  [--now "<当前表述>"] [--source "<判断依据>"] [--by <提交人>] [--degree <熟悉程度>]
```

例（已登记的真勘误）：

```bash
npm run errata -- --loc QH-A-JQ-0001 \
  --text "外部锚点实算1796-02-09为戊申，本条作戊辰朔，与该公历日不相容，须开卷核卷16原文" \
  --now "嘉庆元年正月戊辰朔" \
  --source "1949-10-01=甲子 外部锚点反证（见docs/22 §4.8）"
```

看全部待办：`npm run errata -- --list`

### 口头提也行

你直接说「康熙六十一年那个日期好像不对」，我替你登记并改。命令只是让「记一行」这件事不超过 10 秒。

## 三、`位置ID` 填什么

| 情况 | 填法 | 例 |
|---|---|---|
| 某条主张 | 主张 ID | `QH-A-JQ-0001` |
| 某个争议 | 冲突组 ID | `QH-CF-YZ-NIAN-DEATH` |
| 某个来源台账条目 | 来源 ID | `SRC-062` |
| 某件史料 | 来源单元 ID | `QH-SU-YZ-QSG-0015B` |
| 某个人物 | 人物 ID | `QH-P-000003` |
| 某一章正文 | 章节 slug | `yongzheng-04` |
| 说不清在哪个数据文件 | 页面路由 | `#/claim/QH-A-JQ-0001` |

脚本会核对这个 ID 是否真的存在：**核对不上只警告，仍然写入**——宁可有记录，不要没记录。

## 四、改完之后

1. 改**源文件**（不是改勘误表）：通常是 `data/source-claims.csv`、`data/source-units.csv`、`data/conflict-sets.csv` 或 `content/**` 的正文。
2. 把勘误表该行的 `状态` 从 `待处理` 改为 `已修正`。
   - 状态取值（机器校验）：`待处理` / `已修正` / `不成立` / `重复`。
   - 复核后认为原文没错，标 `不成立`，并**写上理由**——「不成立」不等于「不处理」。
3. 跑一次：

```bash
npm run validate && npm run build
```

`validate` 会检查：`位置ID` 指得到东西（提示级）、`状态` 合法（阻断级）。

---

## 五、红线与边界

- 勘误表是**唯一账本**，别在别处另记一份。
- 改动的原则是**保留原始值＋标注不确定，优于抹平**。发现日期可能不准，不要改写成「约某年」了事，而是保留原值并在 `公历说明` 写明为什么存疑。
- 有异说时**并列保存**，不静默压成唯一答案——这正是本站对爱好者最有用的地方。
- 引文与出处对不上 = 必须改；出处拿不到 = 保留并标注，不算错误。
- **不为了「看起来更严谨」把内容删掉**。宁可留一条标着「待核」的材料，也不要留一片空白。
